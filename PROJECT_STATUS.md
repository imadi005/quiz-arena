### Phase 3 detail

**Implemented:**
- `infrastructure/lib/data-stack.ts` — DynamoDB `Students` table (PK `rollNumber`, GSI on
  `collegeEmail` for duplicate checks).
- `infrastructure/lib/api-stack.ts` — HTTP API with a Cognito JWT authorizer on every route;
  five Lambda handlers in `backend/functions/students/`: create, list, CSV import,
  reset-password, set-status (active/inactive). Each handler independently checks
  `custom:role` is ADMIN or TEACHER before doing anything — the authorizer proves the token is
  valid, the handler decides if that role is allowed.
- Admin never sees an existing password — only `AdminSetUserPassword` (reset to a new
  temporary one) and `AdminCreateUser` (initial temp password) exist as operations.
- Frontend `AdminStudentsPage` now calls the real API: live student list, a working "Add
  Student" modal, CSV import via `papaparse`, and a working reset-password button. No more
  `mockStudents` import in this page.

**Known gap, called out honestly:** email-domain authorization (spec §5) is implemented as a
single env var (`ALLOWED_EMAIL_DOMAINS`) set at deploy time, not an admin-editable setting yet.
Individual-email allowlisting (spec §5 option B) isn't built at all yet. Both are real gaps,
tracked in `TODO_IMPLEMENTATION.md`, not hidden.

**Tested:** `cdk synth` succeeds for all three stacks together (Auth + Data + Api), including
real esbuild bundling of all five Lambda handlers. `npm run build` on the frontend is clean.

**NOT tested — needs you to deploy first:** nobody has run `cdk deploy` for the Data or Api
stacks yet. Until that happens and `VITE_API_URL` is set, the Students page will show "The API
is not configured yet" rather than silently pretending to work.

See `TODO_IMPLEMENTATION.md` for the concrete task breakdown.
